## 1. Executive Summary

Pick Team은 KOSTA 295기 파이널 프로젝트(2025.06~07, 5인 팀)로 개발된 "부트캠프를 위한 올인원 팀 프로젝트 솔루션"이다. 6주 만에 워크스페이스·팀·칸반·캘린더·게시판·SSE 메신저·LiveKit 화상회의까지 동작하는 MVP를 완성했고, CI/CD와 온프레미스 마이그레이션까지 마친 것은 부트캠프 프로젝트 기준으로 상위권 완성도다.

그러나 이 MVP의 결정적 모순은 **기획이 내세운 차별화 포인트가 정확히 미구현 영역과 일치한다**는 것이다. 포스트모템이 핵심 피처로 명시한 세 가지 — ① 멀티 워크스페이스, ② 관리자 승인 기반 진행도 관리, ③ 팀 짜기 — 중 ①만 완성됐다. "성향 기반 팀원 추천"은 메인 페이지의 5대 기능에 올라 있지만, 실제 구현은 MBTI 동일 여부 OR 성향 문자열 LIKE 검색 한 줄짜리 쿼리(`AccountRepository.java:48-50`)이고, 프론트엔드 팀 빌딩 허브는 라우터 미등록으로 세부 페이지 진입이 전부 깨져 있다(`TeamFormationStack.tsx:197-215` vs `Router.tsx:32`). 결과적으로 현재의 Pick Team은 "Slack+Trello+Zoom을 얇게 합친 무언가"이며, 이 형태로는 각 분야 1위 제품과의 비교에서 이길 이유를 설명할 수 없다.

리뉴얼의 핵심 전략은 단순하다. **팀 빌딩을 부가 기능에서 제품의 시작점으로 승격시킨다.** 자기 PR 카드(프로필 필드는 이미 백엔드에 완비돼 있다) → 워크스페이스 스코프의 팀원 탐색 → 지원/스카우트/수락 플로우 → 결성된 팀이 그대로 칸반·채팅·화상회의로 이어지는 여정을 완성하면, "팀을 만드는 것부터 시작하는 협업 툴"이라는 어느 경쟁 제품도 점유하지 않은 포지션을 갖게 된다. 벤치마크했던 유사 서비스 팀바팀(teamby.team)은 현재 접속 불가 상태로, 이 틈새가 여전히 비어 있음을 시사한다.

재개발은 4개 마일스톤으로 진행한다. **M0(안전망)** 는 `Account-Id` 헤더 기반 인증 우회 제거 등 보안 기반 정리(당초 Critical로 기록했던 `.env` git 노출은 2026-07-04 재검증 결과 노출 이력이 없는 것으로 정정됨 — 17 §7 참조. `.env.example`만 신설). **M1(수리)** 은 팀 빌딩 라우트 복구, demo 데이터 페이지의 실 API 연결, 목업 알림의 실동작화 등 "이미 있는 것을 진짜로 만드는" 작업. **M2(엣지 구축)** 가 본편으로, PR 카드 v2와 팀 빌딩 세션, 설명 가능한 규칙 기반 매칭을 구현한다. **M3(차별화 완성)** 는 관리자 승인 워크플로 복원, 온보딩, 성능·폴리시다. 솔로~2인 기준 M0+M1은 3~4주, M2는 5~7주 규모로 추정한다.

가장 큰 열린 리스크는 ① MBTI 중심 매칭의 타당성(강점·역할 중심으로 무게 이동 권고), ② 성향 데이터의 개인정보 처리 이슈(공개 범위 제어 필수), ③ 실사용 검증 채널 부재다. 각각 본문 7장에 검증 방법을 제안했다.

### 2.4 MVP의 강점 (Keep 후보)

1. **범위 대비 실행력**: 6주에 협업 툴 풀스택 + 실시간 2종(SSE, WebRTC/LiveKit) + CI/CD. 커밋 히스토리(2025-06~12)상 배포·보안 판올림까지 지속 관리됨
2. **백엔드 기본기**: 표준 3계층 + QueryDSL, RFC 9457 Problem Details 기반 `GlobalExceptionHandler`, 소프트 삭제 프레임(`BaseSoftDeleteSupportEntity`) + 30일 유예 하드삭제 스케줄러, 테스트 28개 파일
3. **화상회의의 완성도**: LiveKit 자체 호스팅 + 토큰 발급 + Webhook까지 연동 — 개인 프로젝트에서 흔치 않은 자산
4. **도메인 구조의 정합성**: 워크스페이스(과정) → 팀(프로젝트) 2계층이 부트캠프 현실과 일치. 팀 생성 시 칸반·게시판 자동 생성 등 온보딩 마찰을 줄이는 설계 감각
5. **프로세스 자산**: copilot-instructions, CodeRabbit 리뷰 파이프라인, 포스트모템 문화 (「Pick-Team 포스트모템」)

### 2.5 기획 문서와 코드의 주요 갭 요약

- 기획의 차별화 3요소 중 2개(성향 매칭, 승인 기반 진행도 관리 — 후자는 칸반 승인으로 구현됐으나 관리자 대시보드 없이 반쪽)가 미완
- 「화면별 기능 목록 정의」의 "팀 구성 페이지" 항목이 **빈 불릿만 있고 내용이 전무** — 팀 빌딩은 기획 단계에서부터 구체화가 안 된 채 개발에 들어갔다는 직접 증거
- 기능 명세서 자체가 성향 "매칭"을 "랜덤(주사위/사다리)"으로 이미 후퇴시켜 정의 (Epic 2 자동 분배 항목)
- 운영·비용·온보딩·법적 요건을 다룬 문서가 Notion 전체에 존재하지 않음

## 3. Critical Audit Report

각 항목: **[심각도]** 발견 사항 — 근거. 차원별로 심각도 내림차순.

### 3.1 포지셔닝 & 차별화

- **[Critical] "올인원"은 포지셔닝이 아니라 포지셔닝의 부재다.** Slack·Notion·Trello·Zoom의 강점을 각각 얕게 복제하면, 사용자는 각 분야 1위를 떠날 이유가 없다. 팀 스스로도 인지했다: 「다음 발표를 위해 개선할 것들」에 "그래서 우리 서비스를 써야 할 이유 ← 이걸 한 줄로 설명할 수 있어야 함"이라고 적혀 있으나, 이후 어떤 문서에서도 그 한 줄이 완성되지 않았다.
- **[High] 유일하게 방어 가능한 차별화(팀 빌딩)가 실행에서 탈락했고, 발표에서는 포지셔닝을 사후 수정했다.** 「발표 시나리오」 핵심 포인트에서 팀 빌딩이 빠지고 "실시간 화상 채팅"이 1번으로 등장 — 화상회의는 Zoom이 있는 한 차별화가 될 수 없다.
- **[Medium] 타겟 사용자 정의가 '부트캠프'와 '모든 팀 프로젝트' 사이에서 흔들린다.** README는 "팀 프로젝트를 진행하는 모든 사람들", 벤치마크 문서는 "클래스 기반", 포스트모템은 "부트캠프·조별과제·해커톤·게임잼". 타겟이 넓어질수록 관리자(강사) 기능의 우선순위 판단이 불가능해진다.
- **[Low] 시장 신호 미추적.** 벤치마크로 기록된 팀바팀(teamby.team)은 현재 DNS 미해석(접속 불가). 경쟁자 소멸은 기회이자 "이 틈새가 사업이 안 된다"는 경고일 수 있는데 추적 기록이 없다.

### 3.2 기획 품질·완결성

- **[High] 팀 빌딩 기획의 공백.** 「화면별 기능 목록 정의 (작성 중)」의 "팀 구성 페이지" 섹션은 제목 아래 빈 불릿뿐이다. 명세서 Epic 2도 수동 DnD와 랜덤 분배만 정의하고, 메인 페이지가 약속한 "성향 기반 추천"의 요구사항(입력, 알고리즘, 화면, 플로우)은 어느 문서에도 없다.
- **[High] 운영·비용·법적 기획 전무.** 이메일 발송 한도(Gmail SMTP), LiveKit 서버 비용, 파일 스토리지 정책, 이용약관/개인정보 처리방침(MBTI·성향은 프라이버시 민감 데이터), 신고 처리 절차 — 모두 미기획. 「기술력 체크」에서 카카오톡 알림이 "기업회원 한정"으로 좌초된 사례가 이미 있었음에도 법적·정책 요건 검토가 프로세스화되지 않았다.
- **[Medium] 명세가 기능 나열이지 여정이 아니다.** 「다음 발표를 위해 개선할 것들」 스스로 "큰 기능과 작은 기능이 구분이 안 되고 동일선상", "컨트롤러 중심이 아닌 기능 중심으로"라고 반성. 신규 사용자가 가입→워크스페이스 참여→팀 결성→첫 태스크까지 도달하는 여정 정의가 없다.
- **[Low] 미구현 결정의 문서화는 양호.** S3→로컬 업로드, FCM→SSE 대체 등 기술 후퇴는 「기술력 체크」에 취소선과 사유로 남아 있다. 좋은 습관이며 유지할 것.

### 3.3 기능 완성도 (팀 빌딩·프로필 중심)

- **[Critical] 핵심 차별화 기능이 데모 불가능 상태.** §2.3 참조 — 라우트 404, demo 데이터, 플로우 부재, 단순 쿼리. "핵심 기능"이라는 코드 주석(`UserServiceImpl.java:445`)과 실물의 격차가 제품 신뢰도를 훼손하는 수준.
- **[High] 추천 API의 스코프 결함.** 워크스페이스 무관 전체 회원 추천(`AccountRepository.findRecommendedTeamMembers`)은 기능적으로 무의미(다른 과정 사람과 팀을 짤 수 없음)하고 프라이버시 측면에서 위험.
- **[High] 알림 센터가 통째로 목업.** `NotificationsPage.tsx` 하드코딩 + `alert("목업 기능")`. 백엔드에 SSE·`NotificationLog`가 있으므로 연결만 안 된 상태 — 협업 툴에서 알림 부재는 리텐션 직결 결함.
- **[Medium] 채팅 미완 3종.** 채팅방 상세 null 반환, 알림 ON/OFF 빈 메서드 (`ChatRoomServiceImpl.java:192-212`), FE 멤버 입/퇴장 SSE 핸들러 TODO (`ChatContext.tsx:454,459`).
- **[Medium] 팀장 위임 부재로 팀장은 팀을 떠날 수 없음** (`TeamService.java:230-231`). 실사용 시 반드시 부딪히는 운영 결함.
- **[Low] OAuth 콜백 후 초대 코드 처리 TODO** (`OAuthCallbackPage.tsx:98,124`) — 초대 링크로 유입된 소셜 가입자가 워크스페이스에 합류하지 못하는 온보딩 누수.

### 3.4 기술 품질 (아키텍처·부채·확장성)

- **[정정 — 2026-07-04 재검증] `.env`는 git 히스토리에 커밋된 적이 없음.** 최초 감사에서 "Critical: 시크릿이 git에 커밋됨"으로 기록했으나, `git rev-list --objects --all`로 전체 브랜치·전체 오브젝트를 재검사한 결과 `.env`가 어떤 커밋에도 존재하지 않음을 확인했다. `.gitignore`도 이미 `.env`를 정상 제외하고 있고(`application.properties`·`docker-compose.yml`도 전부 `${VAR}` 플레이스홀더만 사용, 하드코딩 없음), 배포는 GitHub Actions Secrets에서 `.env`를 생성해 주입하는 정상 패턴(`deploy.yml`)이다. **실제 문제는 노출이 아니라 온보딩 문서 부재**였다: `.env.example`이 없어 신규 기여자가 필요한 키를 알 수 없었음. → `pick-team-backend/.env.example` 작성 + README 환경변수 섹션 추가로 해소(2026-07-04). 히스토리 정리(filter-repo/BFG)는 **불필요** — 제거할 것이 없다. 로컬 `.env`에는 여전히 실서비스 시크릿이 평문으로 존재하므로, 새 리포로 이관하거나 서브에이전트가 이 워크스페이스에 접근할 때 실수로 복사·커밋하지 않도록 주의가 필요하다(로테이션 자체는 권장 위생이나 더 이상 Critical 사고 대응은 아님).
- **[Critical] 인증 우회 패턴.** `ScheduleController`, `PostController`, `CommentController`, `PostDetailController`, `CommentDetailController`, `PostAttachController`, `AnnouncementController`가 `@RequestParam Long accountId` 또는 `Account-Id` 헤더로 사용자 신원을 수신 — 클라이언트가 임의 ID를 보내 타인 명의로 쓰기 가능. JWT `@AuthenticationPrincipal`로 일원화 필요.
- **[High] 스키마 관리 부재.** `ddl-auto: update` 의존, 마이그레이션 도구(Flyway/Liquibase) 없음. 리뉴얼처럼 스키마가 진화하는 국면에서 데이터 사고의 예고편.
- **[High] N+1 + `JPA_OPEN_IN_VIEW=true`.** 팀 목록 조회 시 팀별 멤버·리더 추가 쿼리(`TeamService.java:256-271`), 전체 사용자 조회 시 사용자별 해시태그 쿼리(`UserServiceImpl.java:607`). OSIV로 컨트롤러 직렬화 시점 지연 로딩까지 겹침.
- **[Medium] FE 상태관리 3중 혼재.** 같은 teamspace 도메인 안에서도 공지/게시판/일정은 Redux, 칸반은 로컬 state, 워크스페이스/채팅/인증은 Context. 신규 기여자의 인지 비용이 크고 캐싱·동기화 전략이 없음.
- **[Medium] 거대 파일.** `TeamKanbanBoard.tsx` 1,902줄(+`any` 다수, `console.log` 10개+), `AuthPage.tsx` 1,170줄(3개 페이지 동거), `sseService.ts` 718줄. 포스트모템의 "컴포넌트 분리가 덜 되어 같은 파일을 계속 건드림" 문제가 여전히 잔존.
- **[Medium] 응답 포맷·예외 처리 불일치.** `AnnouncementController`는 자체 Map 응답 + 자체 `@ExceptionHandler`, 나머지는 `ApiResponse<T>` + 전역 핸들러. `User` 타입에 `bio`/`introduction`, `portfolio`/`portfolioUrl`, 프로필 이미지 필드 3종 병존.
- **[Low] 데드코드·중복.** `ChatPageNew.tsx`(라우터 미등록 구버전, 전송 버튼이 X 아이콘), `maskEmail()` 9개 파일 복붙, FE `userApi` 이중 래핑, `localhost:8081` 하드코딩 폴백 4곳, 구버전 `LOGGING.md` 잔존, FE/BE README 동일 복사본.

### 3.5 UX / 사용자 여정

- **[High] "첫 5분" 여정이 끊겨 있다.** 가입 후 빈 워크스페이스 → 무엇을 해야 하는지 안내 없음. 초대 코드 소셜 가입 플로우 TODO(§3.3)와 겹쳐, 가장 중요한 유입 경로(강사가 뿌린 초대 링크)가 미완.
- **[High] 관리자(강사) 경험 부재.** 타겟의 구매 결정자는 강사/운영진인데, 팀 편성 현황·진행도 집계·미참여자 파악 같은 관리자 대시보드가 없다. 포스트모템의 핵심 피처 ②(승인 기반 진행도 관리)를 뒷받침할 화면이 없는 것.
- **[Medium] 에러·빈 상태 처리 원시적.** 칸반/채팅 실패 시 `alert()`, 일부 페이지 `로딩 중...` 방치, 화상회의 권한 거부 시 안내 없음. `ml-64` 사이드바 하드코딩으로 반응형 미고려.
- **[Medium] React Hook 규칙 위반** — `MyPage.tsx:22` 조건부 `useEffect`. 런타임 불안정 요인.
- **[Low] 발표용 목업 잔재("카카오톡으로 알림 받기" 등)가 실제 UI에 남아 제품 신뢰도를 깎음.**

### 3.6 비즈니스·제품 리스크

- **[High] MBTI 의존 리스크.** MBTI는 재미 요소로는 통하지만 팀 성과 예측 타당성이 낮고, 채용·평가 맥락에서 차별 논란 소지가 있다. 매칭의 주축을 검증 가능한 신호(희망 역할, 기술 스택, 가용 시간, 협업 스타일)로 옮기고 MBTI는 보조·아이스브레이킹으로 격하할 것.
- **[High] 성향·프로필 데이터의 개인정보 이슈.** 성향/워크스타일/MBTI는 프로파일링성 데이터. 수집 동의, 공개 범위(워크스페이스 한정), 삭제권 보장, 처리방침 문서가 필요하나 전무. 현재 추천 API의 전 회원 노출(§3.3)은 이 리스크를 실체화한 상태.
- **[Medium] 운영 비용 미산정.** LiveKit 자체 호스팅(온프레미스), Gmail SMTP 일일 한도, 로컬 파일 스토리지 백업 — 사용자 증가 시나리오별 비용·한계 산정 없음.
- **[Medium] 검증 채널 부재.** 실사용자(부트캠프 1개 기수)를 확보할 경로가 정의돼 있지 않다. 포트폴리오 목적이라도 "실제 기수 1개가 팀 빌딩에 사용" 한 줄이 서사의 무게를 바꾼다.

### 3.8 Unknown Unknowns & 위험한 가정

1. **"부트캠프는 이 툴을 원한다"** — 검증된 적 없음. 강사들은 이미 Slack+Notion 무료 티어에 정착해 있을 수 있다. 전환 비용을 이길 만큼 팀 빌딩 고통이 큰지가 관건.
2. **"성향이 맞으면 좋은 팀이 된다"** — 근거 없는 가정. 실제 부트캠프 팀 갈등의 주원인은 성향보다 실력 격차·투입 시간 격차라는 반론이 유력. 매칭 신호 설계에서 가용 시간·목표 온도(수상 지향 vs 완주 지향)를 포함해야 하는 이유.
3. **"올인원이면 이탈하지 않는다"** — 화상회의 품질이 Zoom보다 낮으면 사용자는 그 기능만 외부로 이탈하고, 이는 올인원 가치 전체를 붕괴시킨다. 모든 기능을 1위 수준으로 만들 수 없다면 "팀 빌딩+진행 관리"에 집중하고 나머지는 '충분히 좋은' 수준으로 유지하는 게 맞다.
4. **LiveKit 온프레미스의 동시 접속 한계 미측정** — 화상회의 몇 팀이 동시에 가능한지 부하 테스트 기록 없음.
5. **로컬 `.env`의 이관·복사 사고 가능성** — 2026-07-04 재검증으로 git 히스토리 내 `.env` 노출은 부정됐으나, 로컬 평문 시크릿을 새 리포나 작업 공유 과정에 실수로 포함할 위험은 남아 있다. 대응은 히스토리 정리가 아니라 `.env.example`, push protection, 시크릿 스캐너, 예방적 로테이션 위생이다.

## 4. Renewed Positioning & Vision

### 4.1 한 문장 포지셔닝

> **"Pick Team은 팀이 '결성되는 순간'부터 함께하는 유일한 협업 툴이다 — 자기 PR 카드로 서로를 알아보고, 맞는 사람과 팀을 만들고, 그 팀이 그대로 협업을 시작한다."**

지지 기둥 3개:
1. **팀 빌딩이 제품의 시작점** — Slack·Trello·Zoom은 "이미 만들어진 팀"을 전제한다. Pick Team만 팀이 존재하기 전 단계(서로 모르는 수강생들)에서 시작한다. 이것이 경쟁 제품이 구조적으로 복제하기 어려운 진입 지점이다.
2. **결성 → 협업의 무단절 전환** — 팀 빌딩에서 만들어진 팀에 칸반·채팅·화상회의가 자동 세팅된다(팀 생성 시 칸반·게시판 자동 생성은 이미 구현돼 있음). "팀 짜고 나서 도구 세팅하는 30분"을 0으로.
3. **관리자(강사)의 가시성** — 팀 편성 현황과 승인 기반 진행도를 한 화면에서. 도입 결정자인 강사에게 파는 가치.

| **수강생** (핵심 사용자) | "나와 목표·시간·스타일이 맞는 팀원을 찾고, 어색한 첫 만남 없이 협업을 시작하고 싶다" | 자기소개 게시판 눈치싸움, 아는 사람끼리 담합, 랜덤 배정 불만 |
| **팀장** (파워 유저) | "역할 분담과 일감 진행을 투명하게 관리하고 싶다" | Trello+카톡 분산, 기록이 흩어짐 |

1차 시장은 **부트캠프(기수제 교육과정)** 로 좁힌다. 조별과제·해커톤은 동일 메커니즘의 2차 확장 시장으로 명시하되 MVP 2.0 범위에서는 제외 — §3.1의 타겟 흔들림을 이 문서로 종결한다.

### 4.3 팀 빌딩 기능의 전략적 역할

팀 빌딩은 기능이 아니라 **유입 장치이자 데이터 자산**이다:
- **유입**: 강사가 "팀 편성을 이걸로 하자"고 하는 순간 기수 전원이 가입한다. B2C 획득 비용 없이 코호트 단위 유입.
- **전환**: 결성된 팀은 이미 Pick Team 안에 있으므로 협업 기능으로의 전환 마찰이 0이다.
- **데이터**: PR 카드·매칭 결과·팀 성과(칸반 완료율)가 쌓이면 "어떤 조합이 완주하는가"라는 이 제품만의 데이터 해자가 생긴다 (장기).
- 벤치마크: 「자기 PR 작성」(프로그래머스 BE4+ 운영 문서)이 증명하듯, 실제 교육 현장은 이미 "PR 작성 기간 → 공개 → 기간제 팀 빌딩" 프로세스를 Notion으로 수동 운영 중이다. **이 수동 프로세스가 우리가 자동화할 대상 그 자체다.** (역할 2개 선택, 강점·협업 스타일·목표 어필, 기간 제한, 사전 접촉 금지 등 구체 규칙을 제품 요구사항으로 흡수)

### 4.4 제품 비전과 North Star Metric

**비전**: "모든 기수제 교육과정에서, 팀 편성일에 열리는 도구."

**North Star Metric**: **팀 빌딩을 통해 결성된 후 2주간 활성 상태(칸반 태스크 1개 이상 갱신)를 유지한 팀 수** — 결성량(팀 빌딩 가치)과 협업 정착(올인원 가치)을 동시에 측정한다.

보조 지표: 워크스페이스 내 PR 카드 작성률(온보딩 품질), 팀 결성 소요 시간(강사 가치), 주간 활성 팀 비율(리텐션), 기능별 사용률(화상회의·채팅이 실제로 쓰이는지 — Cut 판단 근거).

## 5. Feature & Technical Strategy

### 5.1 MVP 2.0 코어 기능셋

```
[진입]   워크스페이스 개설(강사) → 초대 링크 → 가입 + PR 카드 작성 (온보딩 = PR 카드)
[결성]   팀 빌딩 세션 오픈 → 카드 탐색/추천 → 지원·스카우트 → 수락 → 팀 자동 생성
[협업]   칸반(승인 워크플로) + 일정 + 채팅 + 화상회의 + 공지/게시판  ← 기존 자산
[관리]   강사 대시보드: 편성 현황, 미배정자, 팀별 진행도, 승인 큐
[기반]   실동작 알림 센터(SSE), 프로필 공개 범위, 신고/차단
```

### 5.2 기존 기능 처분 결정

§3.7 표를 따르되, 우선순위 관점의 보충:
- **칸반 승인 워크플로**는 이미 구현된 숨은 보석(완료 요청/승인 API 존재). 관리자 대시보드와 연결하는 순간 포스트모템 핵심 피처 ②가 완성된다 — 낮은 비용, 높은 서사 가치.
- **화상회의/채팅은 '충분히 좋은' 수준 유지 전략.** 신규 투자는 버그·미완 구간 수리까지만. 품질 경쟁은 하지 않는다(위험 가정 ③).
- **사다리/주사위 배정은 제거**하고, "랜덤 배정" 옵션 하나로 흡수(강사가 매칭을 원치 않는 경우의 폴백). 유흥성 미니게임이 "성향 기반 매칭" 서사를 희석시킨다.

### 5.3 팀 빌딩 시스템 설계 방향

**(a) 자기 PR 카드 v2** — 기존 `Account` 필드를 재편:

| 필드 | 상태 | 비고 |
|---|---|---|
| 희망 역할 1·2순위 (백엔드/프론트/풀스택/PM/디자인/인프라…) | 신규 | 「자기 PR 작성」의 "최소 2개 역할 선택" 규칙 차용. 매칭 1순위 신호 |
| 기술 스택/강점 태그 | 기존 해시태그 재활용 | `UserHashtag` 인프라 그대로, 추천 로직에 연결 |
| 주간 가용 시간대·투입 가능 시간 | 신규 | 팀 갈등 최대 예측 변수 (§3.8-2) |
| 목표 온도 (수상 지향 ↔ 완주 지향, 5점 척도) | 신규 | 기대치 불일치 예방 |
| 협업 스타일 (기존 `preferWorkstyle`/`dislikeWorkstyle`) | 유지·구조화 | 자유 문자열 → 선택지 + 자유 서술 병행 |
| MBTI | 유지·격하 | 카드 장식 요소로. 매칭 가중치 최하위 또는 0 |
| 자기소개·포트폴리오 링크 | 유지 | |
| **카드 공개 범위** | 신규 | 워크스페이스 한정 공개가 기본값. 법적 리스크(§3.6) 대응의 핵심 |

**(b) 팀 빌딩 세션** — 신규 도메인:
- `TeamBuildingSession`(워크스페이스당, 기간·팀 정원·모집 방식 설정, 강사가 개설) / `TeamApplication`(지원·스카우트·수락·거절 상태 머신)
- 세션 종료 시 미배정자 처리: 강사 수동 배치(기존 `AdminTeamPage` DnD 재활용) 또는 랜덤 폴백
- 수락 완료 → 기존 팀 생성 API 호출 → 칸반·게시판 자동 세팅 (기둥 2 실현)

**(c) 매칭 로직 — 단계적 고도화, 처음부터 설명 가능하게:**
- **v1 (M2)**: 규칙 기반 점수화. `역할 상보성(내 팀에 없는 희망 역할) > 가용 시간 겹침 > 목표 온도 근접 > 스타일 태그 교집합`. 가중치는 상수로 시작. **추천 사유를 반드시 함께 반환** ("프론트엔드 희망 + 저녁 시간대 일치") — 설명 가능성이 신뢰와 차별화의 핵심.
- **v2 (M3+)**: 팀 단위 밸런스 추천(부족 역할 채우기), 강사용 자동 편성 초안 생성.
- **하지 않을 것**: ML/임베딩 기반 매칭. 데이터가 없고, 설명 불가능하며, 솔로 개발 범위를 넘는다.
- 추천 API는 **워크스페이스 스코프 필수** + 카드 공개 동의자만 대상 (§3.3 결함 동시 해소).

**(d) 데이터·프라이버시 요건**: 프로필 항목별 수집 동의(가입 시 아닌 PR 카드 작성 시), 워크스페이스 탈퇴 시 해당 스코프 카드 비공개화, 계정 삭제 시 기존 소프트 삭제→30일 하드삭제 프레임에 PR 카드 포함, 개인정보 처리방침 문서 작성(운영 요건, M2 출시 게이트).
