# 리뉴얼 프론트엔드 구현 기록

이 문서는 `docs/renewal`의 기획을 프론트엔드에 구현하는 진행 상황을 기록한다. 저장소에 GitHub 이슈 기능이 꺼져 있어서 단계 계획과 결정 사항을 이 문서와 각 PR 본문에 남긴다.

## 구현 원칙

### 기존 코드와의 관계

기존 화면 코드(`src/features`, `src/layout`, `src/components` 등)는 지우지 않고 참고용으로 둔다. 리뉴얼 앱은 `src/renewal`에 처음부터 작성하고, `index.html`은 리뉴얼 앱을 띄운다. 기존 코드는 빌드 진입점에서 빠졌지만 타입 검사 대상에는 남아 있다.

### 데이터 계층

화면은 `src/renewal/data/ports.ts`의 포트에만 의존한다. 백엔드 저장소에는 아직 리뉴얼 도메인(PR 카드 v2, 팀 빌딩 세션, 지원·스카우트)이 없으므로 지금은 목 어댑터(`src/renewal/data/mock`)가 포트를 구현한다. 백엔드 API가 생기면 같은 포트를 구현하는 http 어댑터를 추가하고 `src/renewal/data/index.ts`에서 교체한다.

목 어댑터는 브라우저 localStorage(`pickteam.renewal.mock`)에 데이터를 저장한다. 화면 상단의 "목업 데이터" 표시로 실제 데이터와 구분하며, 아바타 메뉴에서 수강생·강사·매니저 계정을 전환해 역할별 화면을 확인할 수 있다. localStorage `pickteam.renewal.mock.fail`에 작업 이름(예: `members,saveCard`)을 넣으면 해당 호출이 실패해 오류 상태를 확인할 수 있다.

서버 상태는 TanStack Query로 관리한다(종합 스펙 §5.4).

### 문서와 문구

화면 문구는 DESIGN.md의 UX 라이팅 기준에 따라 해요체로 쓴다. 문서, 코드 주석, 커밋 메시지, PR 본문은 한다체로 쓴다.

## R1 결정 사항

### 셸 구성

IA §2.1의 글로벌 헤더, WS 레일, 컨텍스트 내비를 구현했다. 반응형은 §2.2를 따른다. 1024px 이상에서는 레일과 내비를 고정하고, 768~1023px에서는 레일만 고정하고 내비를 드로어로 연다. 768px 미만에서는 드로어 안에 레일과 내비를 함께 넣는다.

### 컨텍스트 내비 항목

워크스페이스(홈, 멤버 카드, 팀 빌딩), 관리(대시보드, 세션 운영, 설정), 내 팀, 내 계정 순서로 그린다. 관리 섹션은 개설자와 매니저에게만 보인다. 팀 빌딩 항목은 세션이 없으면 숨기고, 모집 중이면 마감 D-day를 표시한다.

IA §2.3의 공지와 커뮤니케이션(DM, 그룹 채팅, 화상회의) 항목은 아직 넣지 않았다. 해당 화면을 구현하는 단계에서 추가한다. 목업 pr-card-edit.html을 따라 내 계정 섹션(내 PR 카드, 계정 설정)을 내비에 두었다.

### 목업 단계의 인증

실제 인증은 범위 밖이므로 목업 계정 전환으로 대신한다. 아바타 메뉴의 로그아웃은 인증 단계에서 추가한다.

## R2 결정 사항

### 온보딩 위저드(SCR-ONB-01)

목업처럼 셸 없이 단독 화면으로 띄운다. 1단계에서 동의하면 동의 시각을 바로 저장하고, 2단계와 3단계 입력은 계정·워크스페이스별로 브라우저에 임시저장한다. 다시 들어오면 저장된 단계와 값을 복원하고 "처음부터 쓰기"를 함께 보여 준다. 임시저장을 읽지 못하면 11 §5.3의 안내 문구를 보여 준다.

기획은 필수 항목을 채워야 "다음" 버튼이 활성화된다고 적었다. 구현은 버튼을 항상 누를 수 있게 두고, 누르면 빠진 항목에 오류를 표시하고 첫 오류 입력으로 포커스를 옮긴다. 비활성 버튼만으로는 무엇이 빠졌는지 알기 어렵다는 DESIGN.md의 상태 규칙을 따른 결정이다.

3단계에서 "나중에 채우기"를 눌러도 이미 입력한 선택 항목은 버리지 않고 함께 저장한 뒤 카드를 공개한다. 선호 시간대는 목업의 3단계에 없어서 위저드에서 빼고 편집 화면에서만 받는다.

### 내 PR 카드 편집(SCR-MY-02)

/me 경로에는 워크스페이스가 없으므로 컨텍스트 내비는 마지막으로 방문한 워크스페이스를 기준으로 그린다. 필수 섹션과 내용이 있는 섹션은 펼친 상태로 시작하고, 저장할 때 오류가 있으면 해당 섹션을 펼치고 첫 오류 입력으로 포커스를 옮긴다. 저장하지 않은 변경이 있을 때 취소하면 확인 대화상자를 띄운다. 동의 전 사용자에게는 편집 폼 대신 동의 안내를 먼저 보여 준다.

공개 스위치는 필수 항목이 비어 있으면 켤 수 없고, 그 이유를 스위치 옆에 적는다. 공개 여부는 다른 필드와 함께 저장 버튼으로 반영한다.

### 필드 해석

MBTI는 "선택 안 함(카드에 표시 안 함)"을 포함한 선택 하나로 처리한다. 11-D4 결정에 따라 표시하지 않으면 매칭에서도 쓰지 않으므로 별도의 숨김 플래그를 두지 않았다. 희망 역할에서 "기타"를 고르면 역할 이름(20자)을 받는다. 1순위로 고른 역할은 2순위에서 고를 수 없고, 선호로 고른 협업 스타일은 기피에서 고를 수 없다. 기술 태그는 기존 UserHashtag 검증 규칙(한글, 영문, 숫자, 밑줄, 2~20자, 최대 20개)을 따른다.

### 아직 없는 화면

개인정보 처리방침 링크는 준비 중 화면으로 연결한다(17번 문서 범위). 프로필 사진은 목업 저장소 용량 때문에 256px JPEG로 줄여 저장하며, 실제 업로드는 http 어댑터에서 기존 `POST /api/users/me/profile-image`로 연결할 예정이다.

## R3 결정 사항

### 갤러리 목록 구성(SCR-WS-02)

공개 카드를 먼저 보여 주고, 카드를 작성하지 않은 멤버는 뒤쪽에 흐린 자리 표시로 둔다(11-D3). 비공개 카드는 11 §5.2에 따라 목록에서 뺀다. 내 카드가 공개 상태가 아니면 목록 위에 "다른 멤버에게 보이지 않는다"는 안내와 해결 링크를 띄운다. 상단 수치는 "전체 N명, 카드 공개 M명"으로 표시한다. 목업의 "작성 완료"는 비공개 카드를 포함하는지가 모호해서, 실제로 목록에 보이는 수를 기준으로 했다.

### 필터

필터 상태는 주소 쿼리(`role`, `hours`, `tags`)에 담아 링크를 공유하거나 새로 고쳐도 유지된다. 필터를 바꿀 때는 기록을 덮어써서 뒤로 가기가 이전 화면으로 이동한다. 서로 다른 필터는 AND로 묶는다. 역할 필터는 고른 역할이 1순위나 2순위에 있으면 통과하고, 태그 필터는 고른 태그를 모두 가진 카드만 통과한다. 필터가 걸려 있으면 미작성 자리 표시는 숨긴다. 목업은 역할을 드롭다운 두 개로 그렸지만 기획(11 §4.4)이 다중 선택을 요구해 토글 칩으로 바꿨다.

### 카드 상세(SCR-PRF-01)

목업은 상세를 갤러리 위의 오버레이로 그렸지만, IA의 URL(`/ws/:wsId/members/:accountId`)을 따르기 위해 별도 페이지로 만들었다. 워크스페이스에 속하지 않은 멤버나 존재하지 않는 멤버는 404 화면을 보여 준다. 비공개와 미작성 카드는 이름과 사진만 보여 주고 안내 문구를 띄운다. 스카우트 제안 버튼은 팀 빌딩 멤버 화면(SCR-TB-01~03)을 구현할 때 붙인다.

### 데이터

멤버 응답에 `cardState`(PUBLIC, PRIVATE, NOT_WRITTEN)를 추가했다. 비공개 카드의 내용은 서버가 내려보내지 않는다는 전제를 목 어댑터에 반영했다. 존재하지 않음, 권한 없음처럼 다시 시도해도 결과가 같은 오류는 쿼리를 재시도하지 않는다.

## R4 결정 사항

### 화면 구성(SCR-WS-01)

목업 workspace-home.html을 따라 인사, 내 상태 요약 3열, 최근 공지, 멤버 카드 미리보기 순서로 배치했다. 요약 카드는 화면 폭에 따라 3열, 2열, 1열로 바뀐다.

| 요약 카드 | 표시 조건과 내용 |
|---|---|
| 내 팀 | 항상 표시한다. 팀이 있으면 팀원 아바타, 팀 이름, 팀원 수, 팀 스페이스 이동 버튼을 보여 준다. |
| 팀 빌딩 | 세션이 있고 DRAFT가 아닐 때 표시한다. OPEN이면 D-day, 마감 시각, 팀 없는 멤버 수와 팀 빌딩·제안함 버튼을, CLOSING과 RESOLVED면 상태 안내를 보여 준다. |
| PR 카드 | 내 카드가 공개 상태가 아닐 때만 표시한다(10 §5 "카드 작성 완료 전까지 상시"). 워크스페이스 카드 공개율을 함께 보여 준다. |

### 목업과 다르게 처리한 부분

목업의 내 팀 카드에 있던 "칸반 완료 60%"는 칸반 데이터를 연결하지 않아 표시하지 않았다. 팀 스페이스 단계에서 실제 완료율을 연결할 때 추가한다. 목업의 작성률은 "카드 공개율"로 표기했다. 갤러리와 같은 기준(공개 카드 수 / 전체 멤버 수)이다. 인사 문구의 이모지는 넣지 않았다.

### 공지 데이터

최근 공지는 기존 백엔드 AnnouncementController의 응답 형태(제목, 작성자, 팀, 작성 시각)를 따르는 포트로 받는다. 팀 공지는 그 팀 멤버에게만 보이고 워크스페이스 전체 공지는 모두에게 보인다. 공지 전체 목록 화면은 아직 없어서 "모두 보기" 링크를 두지 않았다.

### 역할별 진입점

IA §4와 02-D4는 개설자·매니저가 처음 들어올 때 대시보드로 보내도록 정했다. 대시보드는 R6에서 구현하므로 진입점 분기도 R6에서 붙인다.

## R5 결정 사항

### 단계 순서 조정

목업 목록(index.html)은 team-building-session.html을 SCR-TB-04로 소개하지만, 실제 시안은 수강생 시점의 팀 빌딩 홈, 팀 상세, 제안함을 그린다. 시안 내용을 따라 R5에서 SCR-TB-01~03을 구현하고, 세션 운영(SCR-TB-04)과 강사 대시보드(SCR-DSH-01)는 R6으로 옮겼다. SCR-TB-04는 시안이 없으므로 12 §4.4의 와이어프레임을 근거로 삼는다.

### 매칭과 규칙

매칭 v1은 `src/renewal/domain/matching.ts`에 순수 함수로 두었다. 가중치는 12 §5.3을 따라 역할 40, 시간대 25, 목표 온도 20, 협업 스타일 15이며 MBTI는 0이다. 화면에는 점수 대신 별 5단계(12-D2)와 상위 사유 2개만 보여 준다.

지원·스카우트 규칙은 `src/renewal/data/mock/rules.ts`에 모았다. 백엔드가 지켜야 할 12 §6.1.1 불변조건을 목 어댑터가 같은 방식으로 검사한다.

12 §5.2는 정원이 차면 "받은 지원"만 정리한다고 적었다. 팀이 보낸 스카우트가 남아 있으면 수락할 수 없는 제안이 대기 상태로 남으므로 함께 철회한다. 팀 개설 시 자동 철회는 기획에 명시되지 않았지만, 한 세션에서 한 팀에만 소속한다는 규칙에서 끌어낸 해석이다. 백엔드 설계 때 두 항목을 확인해야 한다.

| 규칙 | 근거 |
|---|---|
| 지원과 팀 개설에는 공개 카드가 필요하다 | 01-D1, 11-D5 |
| 개설자와 매니저는 지원·스카우트의 당사자가 아니다 | 12 §2 |
| 스카우트는 팀장만 보낼 수 있다 | 12-D1 |
| 답변 대기 중인 지원은 3건까지다 | 12-D4 |
| 수락하면 합류한 사람의 다른 대기 제안은 자동 철회한다 | 12 §5.2 |
| 수락으로 정원이 차면 그 팀이 받은 대기 지원은 거절, 보낸 대기 스카우트는 철회로 끝내고 사유를 정원 마감으로 남긴다 | 12 §5.2 |
| 팀을 만들면 내가 보낸 대기 지원은 자동 철회한다 | 구현 해석 |

### 팀 빌딩 홈(SCR-TB-01)

상단 띠에 내 소속, 보낸·받은 대기 제안 수, 마감까지 남은 날을 모아 이 화면의 분기 기준으로 삼았다. 팀이 없으면 팀을 추천하고, 팀이 있으면 사람을 추천한다. 사람 추천의 스카우트 버튼은 팀장에게만 보이고, 팀원에게는 이유를 글자로 적는다. 카드가 공개 상태가 아니면 추천 대신 카드 작성 안내를 띄우고, 지원이나 팀 만들기를 누르면 카드 작성으로 안내하는 대화상자를 연다.

세션 상태별 화면은 다음과 같다. 세션이 없으면 매니저에게는 세션 운영으로 가는 버튼을, 멤버에게는 안내만 보여 준다. DRAFT는 멤버에게 준비 중 안내와 카드 편집 링크를 보여 준다. CLOSING은 새 지원과 스카우트를 받지 않는다고 알리고, RESOLVED는 팀 스페이스로 가는 버튼을 보여 준다.

팀 만들기 대화상자는 모집 인원 합계가 정원에서 나를 뺀 자리 수를 넘지 않게 막는다. 팀 이름과 모집 역할이 비어 있으면 해당 입력으로 포커스를 옮긴다.

### 팀 모집 상세(SCR-TB-02)

팀원 카드 요약과 팀 단위 집계(공통 가용 시간, 평균 목표 온도)를 보여 준다. 12-D6에 따라 팀원 개인의 가용 시간과 목표 온도는 이 화면에 따로 노출하지 않는다. 와이어프레임의 역할별 대기 수("백엔드 1, 지원 2 대기")는 지원 데이터에 역할 정보가 없어 전체 대기 수로 대신했다.

팀장에게는 오른쪽 패널이 받은 지원 관리로 바뀐다(12 §4.2). 대기 중인 지원을 위에 두고, 끝난 지원은 흐리게 남긴다.

### 제안함(SCR-TB-03)

받은 제안과 보낸 제안을 탭으로 나누고, 고른 탭을 주소 쿼리(`?tab=sent`)에 남긴다. 탭은 화살표, Home, End 키로 옮길 수 있다. 대기 중인 제안을 먼저, 끝난 제안은 흐리게 두고 상태 배지와 사유를 글자로 남긴다.

수락은 합류를 확정하고 다른 제안도 함께 끝내므로 확인 대화상자에서 결과를 한 문장으로 알린다. 건수는 `src/renewal/domain/proposals.ts`가 목 규칙과 같은 기준으로 계산한다. 팀장이 지원을 수락할 때는 지원자가 다른 팀에 보낸 지원이 팀장에게 보이지 않으므로 그 건수는 세지 않는다. 거절과 철회는 한 건만 바꾸므로 확인 없이 처리하고 토스트로 결과를 알린다. 모집이 끝난 세션에서는 수락, 거절, 철회 버튼을 숨긴다.

### 스카우트 진입점

R3에서 미뤄 둔 카드 상세의 스카우트 버튼을 붙였다. 모집 중인 세션에서 빈자리가 있는 팀의 팀장에게만 보이고, 대상은 팀이 없는 공개 카드 멤버로 한정한다. 이미 보낸 스카우트가 대기 중이면 버튼 대신 상태 배지를 보여 준다.

### 아직 없는 연결

12 §4.3은 제안함을 알림 딥링크의 도착 지점으로 정했다. 알림 센터가 아직 없어서 딥링크는 연결하지 않았다. 팀 상세의 팀 소개와 모집 역할을 수정하는 기능은 기획에 화면이 없어 넣지 않았다.

## R6 결정 사항

### 세션 운영(SCR-TB-04)

12 §4.4 와이어프레임과 §5.1 상태 머신을 따른다. 시안이 없어서 화면 구성은 R5 화면의 패턴(상단 상태, 현황 수치, 목록과 보드)에 맞췄다. 상태별로 할 수 있는 일은 다음과 같다.

| 상태 | 화면 | 조작 |
|---|---|---|
| 세션 없음 | 세션 만들기 폼 | 모집 마감, 팀 정원을 정해 DRAFT로 만든다 |
| DRAFT | 설정 폼과 현황 | 설정 저장, 모집 시작 |
| OPEN | 현황 모니터 | 마감 연장, 지금 마감, 카드 미작성자 리마인드 |
| CLOSING | 미배정 목록과 팀 보드 | 수동 배치, 배치 취소, 새 팀 슬롯, 남은 미배정자 랜덤 배치, 결과 확정 |
| RESOLVED | 결과 요약 | 없음(12-D5 재오픈 불가) |

규칙은 `src/renewal/data/mock/sessionRules.ts`에 순수 함수로 두고 테스트했다. 모집 시작, 지금 마감, 결과 확정은 되돌릴 수 없으므로 결과를 한 문장으로 알리는 확인을 거친다. 지금 마감은 답변을 기다리던 제안을 사유 "모집 마감"으로 만료한다(12 §5.2). 결과 확정은 미배정이 0명일 때만 할 수 있고, 아무도 배치되지 않은 팀 슬롯은 함께 지운다.

### 기획과 다르게 처리한 부분

기획은 수동 배치를 드래그 앤 드롭으로 그렸다. 키보드와 보조기기로도 같은 일을 할 수 있도록 미배정 멤버마다 팀 선택 목록과 "배치" 버튼을 두었다. 드래그는 이후 보조 수단으로 추가할 수 있다.

DRAFT 설정은 모집 마감과 단일 팀 정원(2~8명)만 받는다. 기획의 정원 min/max, 구성 방식, 팀 개설 권한은 아직 도메인에 없다. 팀 개설 권한은 01-D2 결정(멤버 누구나 개설)을 그대로 쓴다. 모집 중에는 이미 꾸린 팀이 정원을 넘을 수 있어서 정원을 바꿀 수 없게 했다.

랜덤 배치는 12 §5.4-6의 "역할 분포를 고려한 제약 랜덤"을 이렇게 해석했다. 미배정자 순서를 섞고, 사람마다 빈자리가 있는 팀 중 같은 1순위 역할이 가장 적은 팀, 그다음 인원이 가장 적은 팀을 고른다. 빈자리가 모자라면 배치한 인원과 남은 인원을 알리고 새 팀 슬롯 추가를 안내한다. 빈 팀 슬롯에 처음 배치한 사람이 잠정 팀장이 되고, 팀장을 빼면 남은 팀원 중 먼저 합류한 사람이 팀장을 이어받는다.

마감 시각이 지나도 목 어댑터는 세션을 자동으로 CLOSING으로 바꾸지 않는다. 시각에 따른 전이는 서버 스케줄러가 맡을 일이라 화면에서는 "지금 마감"만 다룬다.

### 강사 대시보드(SCR-DSH-01)

목업 instructor-dashboard.html의 위젯 4종과 승인 큐를 구현했다. 화면에서는 "위젯 A~D" 표기를 빼고 제목만 보여 준다.

| 위젯 | 내용 |
|---|---|
| 가입·카드 현황 | 가입 인원과 워크스페이스 정원, 참여 멤버 기준 카드 작성률, 미작성자 리마인드 |
| 팀 빌딩 현황 | 세션 상태, 마감, 배정·미배정 인원, 세션 운영 링크. 세션이 없으면 세션 만들기 링크 |
| 진행도 보드 | 팀별 칸반 완료율과 승인 대기 수. 13-D1에 따라 팀 내부 내용은 보여 주지 않는다 |
| 이상 신호 | 7일 이상 칸반 갱신이 없는 팀, 이번 기수 차단 이력 |
| 승인 큐 | 승인 대기 태스크, 상세 보기(팀 칸반), 승인. 승인자는 지금 로그인한 계정으로 기록한다 |

카드 작성률의 분모는 팀 빌딩 참여 대상(멤버 역할)이다. 개설자와 매니저는 카드를 쓰지 않아도 되므로 목업의 "가입 14명 중 작성 10명"처럼 전체 가입자를 분모로 쓰면 작성률이 실제보다 낮아진다. "작성"은 공개와 비공개 카드를 모두 포함한다.

### 아직 실제 데이터가 없는 부분

칸반, 승인, 차단, 알림 기능이 리뉴얼 앱에 아직 없어서 진행도, 승인 대기, 차단 이력은 목 저장소의 시드 값이다. 리마인드는 발송 기록만 남기고 실제 알림은 보내지 않는다. 승인 큐의 상세 보기와 팀 칸반 링크는 준비 중 화면으로 연결된다. 목업의 이상 신호 행동(공지 보내기, 멤버 상세)은 공지 작성과 멤버 관리 화면이 생기면 붙인다.

### 매니저 진입 경로(02-D4, 13 §5.4)

개설자·매니저가 워크스페이스에 처음 들어오면 대시보드로 보내고, 이후에는 그 워크스페이스에서 마지막으로 본 화면으로 보낸다. 마지막 화면은 계정과 워크스페이스별로 브라우저에 기억한다(`src/renewal/shell/entry.ts`). 진입점은 앱 첫 화면과 WS 레일이다. 내비의 "홈" 링크는 진입이 아니라 이동이므로 언제나 홈으로 간다. 멤버는 지금처럼 홈으로 들어간다.

### 권한 안내와 내비

멤버가 대시보드나 세션 운영 주소로 들어오면 404 대신 권한 안내를 보여 준다(02-D2: 관리 화면은 403 안내). 세션 운영 메뉴는 세션이 없어도 개설자·매니저에게 보여 세션을 만들 수 있게 했다(12 §5.4-8). 세션 운영 화면에서는 팀 빌딩 메뉴를 활성으로 표시하지 않는다.

## R7 결정 사항

### 범위

목업이 없는 단계라 10번 기획의 와이어프레임과 엣지 케이스(§4, §5.3)를 근거로 삼았다. 화면 구성은 R2 온보딩처럼 셸 없는 가운데 카드로 맞췄다.

| 화면 | 경로 | 내용 |
|---|---|---|
| SCR-AUTH-01 로그인 | `/login` | 인라인 오류, 비밀번호 보기, OAuth 버튼, 초대 안내 |
| SCR-AUTH-02 가입 | `/signup` | 이메일, 인증 코드(5분), 이름·비밀번호의 3단계 |
| SCR-AUTH-03 비밀번호 재설정 | `/reset-password` | 이메일, 재설정 코드, 새 비밀번호의 3단계와 완료 화면 |
| SCR-AUTH-04 초대 랜딩 | `/invite/:code` | 워크스페이스 이름·개설자·만료일, 가입·로그인 분기, 로그인 상태의 참여 버튼, 합류 비밀번호(10-D4) |
| OAuth 콜백 | `/oauth/callback` | 임시 코드 교환 후 이메일 가입과 같은 경로로 합류를 잇는다 |
| SCR-WS-04 무소속 랜딩 | `/welcome` | 초대 코드·링크로 참여, 새 워크스페이스 만들기 |

인증 화면과 초대 랜딩을 뺀 모든 화면은 `RequireAuth` 아래에 두었다. 미인증으로 들어오면 원래 목적지를 `redirect` 쿼리에 담아 로그인으로 보낸다(10 §2). 로그인한 사람이 인증 화면에 오면 원래 목적지나 첫 화면으로 보낸다. 계정 메뉴에 로그아웃을 추가했고, WS 레일 맨 아래에 참여·만들기 버튼을 두었다. 768px 미만에서는 워크스페이스 밖(`/welcome`)에서도 메뉴 버튼으로 레일을 열 수 있다.

### 초대 합류 흐름

초대 코드는 기획대로 sessionStorage의 `pendingInviteCode`에 보존한다(10 §5.2). 합류 처리는 초대 랜딩 한곳에 모았다. 로그인, 가입, OAuth를 마치면 보존한 코드가 있을 때 `/invite/:code?join=1`로 돌아오고, 비밀번호가 없는 워크스페이스는 바로 합류한다. 비밀번호가 있으면 랜딩에서 비밀번호를 받는다. 이렇게 하면 세 인증 경로가 같은 합류 코드를 쓰고, 합류에 실패해도 같은 화면에서 다시 시도할 수 있다.

| 상황 | 처리 |
|---|---|
| 합류 성공 | 카드가 없으면 온보딩(10 §4.5 진입 조건), 있으면 홈으로 간다 |
| 이미 멤버 | 홈으로 보내고 "이미 참여 중인 워크스페이스예요" 토스트를 띄운다 |
| 차단·정원 초과·만료 | 인라인 오류를 보여 주고 보존한 코드를 지운다 |
| 네트워크 오류 | 코드를 남겨 두고 다시 시도할 수 있게 한다 |
| 없는 코드 / 만료·재발급된 코드 | 각각 NOT_FOUND와 GONE으로 나눠 안내하고 가입·로그인 버튼을 보여 주지 않는다 |

무소속 랜딩의 초대 코드 입력은 코드를 확인만 하고 초대 랜딩으로 넘긴다. 강사가 보낸 링크 전체를 붙여 넣어도 코드를 꺼내 쓴다.

### 보안 관련 결정

로그인 오류는 이메일과 비밀번호를 구분하지 않는 한 문구로 알린다. 비밀번호 재설정 코드 요청은 가입되지 않은 이메일이어도 같은 안내로 끝낸다. 가입은 이미 있는 이메일을 알려야 다음 행동(로그인)을 안내할 수 있어 예외로 두었다.

`redirect` 쿼리는 앱 안의 경로만 따른다(`safeRedirect`). `//`나 `/\`로 시작하는 주소와 인증 화면으로 되돌아가는 주소는 무시한다. 열린 리다이렉트로 다른 사이트에 보내는 공격을 막기 위해서다.

OAuth로 들어온 이메일이 이미 이메일 계정에 있으면 자동 병합하지 않고 안내한다(10-D3). 비밀번호 재설정에 쓴 코드는 바로 지워 다시 쓸 수 없다(10 §5.3, 백엔드 AuthServiceImpl TODO).

### 기획·백엔드와 다른 부분

기획은 가입 3단계에서 닉네임을 받지만 백엔드 `SignupRequest`에는 이름 필드가 없다. 화면은 이름을 받고, http 어댑터를 붙일 때 가입 DTO를 바꾸거나 가입 직후 프로필 수정 API를 함께 불러야 한다.

비밀번호 조건은 백엔드 DTO를 따른다. 가입은 대문자·소문자·숫자·특수문자(`!@#$%^&*()-=`)를 모두 요구하고, 재설정은 영문·숫자·특수문자(`@$!%*?&`)만 허용한다. 두 규칙이 서로 달라 화면도 각각 따르며, 백엔드에서 규칙을 하나로 맞추는 편이 좋다.

워크스페이스 만들기는 13번 기획의 설정 화면(SCR-WS-03) 전에 필요한 최소 기능으로 이름과 합류 비밀번호만 받는다. 만들면 30일짜리 초대 링크를 함께 발급한다(10-D2). 초대 링크 재발급과 사용 횟수 화면은 SCR-WS-03 초대 탭에서 다룬다.

### 목 데이터

목 저장소에 계정 비밀번호(SHA-256 해시), 인증 코드, 초대 링크 v2(만료일, 활성 여부, 사용 횟수), OAuth 연결을 추가했다. 해시는 브라우저 저장소에 평문 비밀번호를 남기지 않으려는 장치일 뿐 실제 보안 수단이 아니다. 목업 데이터일 때만 화면에 시드 계정과 발송한 인증 코드를 "목업 안내"로 보여 준다.

| 시연 데이터 | 값 |
|---|---|
| 시드 계정 | user1@example.com(김수강)~user15@example.com(홍길동, ws-1 차단 이력), 비밀번호 `Pickteam1!` |
| 유효한 초대 | `SUMMER26`(ws-1, 30일), `ALGO2026`(ws-2, 만료 없음), `UXSTUDY`(ws-3, 합류 비밀번호 `study`) |
| 쓸 수 없는 초대 | `SPRING26`(만료), `UXOLD`(재발급으로 무효) |
| OAuth 이메일 중복 재현 | localStorage `pickteam.renewal.mock.fail`에 `oauthConflict` |

OAuth 버튼은 목업에서 제공자 화면 없이 바로 콜백으로 돌아온다. http 어댑터에서는 `oauthStartUrl`이 백엔드 OAuth 시작 주소를 돌려주면 된다.

### 아직 없는 것

이메일 발송 속도 제한(10-D1)과 Refresh Token 저장 위치(10-D5)는 백엔드 범위다. 계정 설정의 OAuth 연동, 초대 링크 발급·재발급 화면은 각각 SCR-MY-03과 SCR-WS-03 단계에서 구현한다.

## R8 결정 사항

### 단계 나누기

14번 기획의 팀 스페이스 화면 6개를 세 단계로 나눴다. R8은 공통 틀과 개요·칸반, R9는 일정·게시판·공지, R10은 팀 설정(위임·내보내기·삭제)이다. 아직 구현하지 않은 탭은 팀 스페이스 틀 안에서 준비 중 화면으로 연결했다.

### 팀 스페이스 틀과 접근

`/ws/:wsId/team/:teamId` 아래에 팀 이름, 인원, 탭(개요, 칸반, 일정, 게시판, 공지, 팀 설정)을 두었다. 탭은 화면을 바꾸는 링크라 ARIA 탭이 아니라 내비게이션으로 표시한다.

| 들어온 사람 | 처리 | 근거 |
|---|---|---|
| 팀원(팀장 포함) | 모든 탭 | 14 §2 |
| 팀원이 아닌 개설자·매니저 | 개요(집계)와 칸반(읽기, 승인·반려)만. 다른 탭 주소로 오면 팀원 전용 안내 | 13-D1, 14 §2, 13 §4.5 |
| 팀원이 아닌 멤버 | 404로 팀의 존재를 숨긴다 | 02-D2 |

매니저에게 칸반을 열어 둔 것은 13 §4.5 승인 큐의 "상세 보기"가 SCR-TM-02로 이동하기 때문이다. 대신 매니저는 태스크를 만들거나 고치거나 댓글을 달 수 없고, 승인과 반려만 한다.

### 팀 개요(SCR-TM-01)

팀원 카드 요약(희망 역할, 태그 3개), 칸반 진행도(완료율과 상태별 수), 다음 일정, 최근 공지를 보여 준다. 승인 대기 수는 팀장과 매니저에게만 강조한다. 칸반과 일정이 모두 비어 있으면 결성 직후 체크리스트(역할 확정, 첫 회의 일정, 첫 태스크)를 먼저 보여 준다. "역할 확정"은 데이터로 판단할 수 없어 팀장이 "확정했어요"로 표시하게 했다. 다음 일정에는 개인 일정을 넣지 않고, 매니저에게는 일정과 공지를 보여 주지 않는다(13-D1).

### 칸반(SCR-TM-02)

할 일, 진행 중, 완료 요청, 완료(승인) 네 칸으로 승인 워크플로를 드러냈다. 권한은 `domain/kanban.ts`의 `availableActions` 하나로 정하고 화면 버튼과 목 규칙이 같이 쓴다.

| 행동 | 할 수 있는 사람 | 비고 |
|---|---|---|
| 진행 시작, 할 일로 되돌리기 | 팀원 | |
| 완료 요청 | 담당자 | 담당자가 없으면 "담당자를 먼저 배정해야 완료 요청을 할 수 있어요"(14 §5.2) |
| 승인, 반려 | 팀장, 매니저 | 반려는 사유 필수. 승인자와 시각을 기록한다 |
| 다시 열기 | 팀장 | 완료된 태스크를 진행 중으로 되돌린다(기획에 없는 보완) |
| 삭제 | 만든 사람, 팀장 | 확인 대화상자를 거친다 |

카드 이동은 상세의 버튼으로 한다. 드래그만으로 옮기는 방식은 키보드로 쓸 수 없어 두지 않았다(R6 수동 배치와 같은 결정). 담당자가 팀원이 아니면 조용히 넘기지 않고 "담당자가 팀원 목록에 없어요"로 알린다. 마감일이 지난 미완료 태스크에는 "마감 초과" 배지를, 반려된 태스크에는 "반려됨" 배지를 붙인다. 필터(`?filter=pending`)와 열린 태스크(`?task=`)는 주소에 남겨 대시보드 승인 큐의 "상세 보기"가 해당 태스크를 바로 연다.

### 백엔드와 다른 모델

백엔드 칸반은 사용자 정의 리스트(`KanbanList`)와 `isApproved`, `completionRequested` 플래그로 상태를 표현한다. 화면은 기획대로 상태 4개를 쓰므로 http 어댑터에서 리스트와 플래그를 상태로 바꾸는 매핑이 필요하다. 승인자 기록(`approvedBy`, `approvedAt`)과 반려 사유는 14 §6.2대로 백엔드 필드 추가가 필요하다.

### 대시보드 연결

R6 대시보드의 진행도, 승인 대기, 무활동 신호는 목 저장소의 별도 시드 값이었다. 이제 모두 칸반 태스크에서 계산한다. 대시보드의 승인 버튼도 칸반 승인 규칙으로 처리하므로 대시보드와 칸반의 상태가 어긋나지 않는다. 시드 태스크는 R6 시연 값(완료율 60%, 40%, 80%, 승인 대기 3건, 8일 무활동)을 그대로 재현한다. 팀원이 아닌 매니저가 승인하면 승인 기록에 "이름(매니저)"로 표시한다.

## R9 결정 사항

### 권한

권한은 `domain/collab.ts`에 모아 화면과 목 규칙이 같이 쓴다. 세 화면 모두 팀원 전용이며, 팀원이 아닌 매니저가 주소로 오면 팀원 전용 안내를 보여 준다(13-D1).

| 대상 | 수정·삭제할 수 있는 사람 | 근거 |
|---|---|---|
| 팀 일정 | 만든 사람, 팀장 | 14 §2 |
| 개인 일정 | 만든 사람. 다른 사람에게는 목록에서부터 빠지고, 주소로 접근해도 없는 것처럼 다룬다 | 14 §4.3, §5.3 |
| 게시글, 댓글 | 쓴 사람, 팀장 | 14 §2 |
| 팀 공지 | 팀장 | 14 §2 |

팀장이 남이 만든 팀 일정을 개인 일정으로 바꾸면 만든 사람에게서 일정이 사라지므로, 개인 일정 전환은 만든 사람만 할 수 있게 했다.

### 일정(SCR-TM-03)

월간, 주간, 리스트 보기와 팀 일정·내 일정 레이어를 두었다. 보기와 기준 날짜는 주소(`?view=`, `?date=`)에 남긴다. 유형 5종(14-D3)은 색과 함께 유형 이름을 글자로 보여 준다. 월간 보기는 표로 그려 요일 머리글과 날짜를 읽을 수 있게 했고, 640px 미만에서는 일정 제목 대신 유형 점과 개수를 보여 주며 누르면 그 주를 주간 보기로 연다. 여러 날에 걸친 일정은 걸친 날마다 보인다.

기획의 주간 보기는 "시간대별 세로 레인"이지만, 요일별 칸에 시간순 목록으로 단순화했다. 시간 레인은 겹치는 일정 배치와 키보드 탐색 설계가 함께 필요해 이후 개선으로 남긴다. 일정 리마인더는 알림 센터(16)가 없어 넣지 않았다.

### 게시판(SCR-TM-04)

목록에서 제목, 작성자, 날짜, 댓글 수를 보여 주고 글은 상세 주소(`board/:postId`)로 연다. 글을 올리면 바로 상세로 이동하고, 지우면 목록으로 돌아간다. 첨부 파일은 목 저장소에 파일을 담을 수 없어 넣지 않았다. http 어댑터에서 기존 `PostAttachController`로 연결해야 한다.

### 팀 공지(SCR-TM-05)

공지는 팀장만 쓰고 고친다. 팀 공지는 워크스페이스 홈의 최근 공지와 팀 개요의 최근 공지에 함께 실린다. 기획 14 §2는 매니저도 팀 공지를 쓸 수 있다고 적었지만, 13-D1에 따라 매니저는 팀 내부 화면을 보지 않으므로 팀 공지 화면에서는 팀장만 쓰게 했다. 매니저가 모든 팀에 알릴 내용은 워크스페이스 공지(아직 화면 없음)로 다루는 편이 맞다. 공지 알림(16 연동)은 알림 센터 단계에서 붙인다.

## R10 결정 사항

### 화면 구성(SCR-TM-06)

기본 정보, 팀장 위임, 멤버, 팀 나가기, 팀 삭제 다섯 구역을 한 화면에 두었다. As-Is의 드롭다운과 `prompt()` 확인을 모두 대체한다. 권한은 목 규칙 `data/mock/teamSettingsRules.ts`에 모았다.

| 행동 | 할 수 있는 사람 | 비고 |
|---|---|---|
| 이름·소개 수정 | 팀장 | 같은 워크스페이스에 같은 이름의 팀이 있으면 막는다 |
| 위임 지명·취소 | 팀장 | 진행 중인 요청이 있으면 새로 지명할 수 없다 |
| 위임 수락·거절 | 지명된 팀원 | 24시간이 지나면 만료(14 §5.4) |
| 팀원 내보내기 | 팀장, 개설자·매니저 | 팀장은 내보낼 수 없다. 내보낸 사람은 담당 태스크에서도 빠진다 |
| 팀 나가기 | 팀원 | 팀장은 위임을 마친 뒤 나간다. 혼자 남은 팀장이 나가면 팀을 해체한다 |
| 팀 삭제 | 팀장, 개설자·매니저 | 팀 이름을 그대로 입력해야 삭제 버튼이 켜진다(14 §5.5) |

팀원이 아닌 매니저도 팀원 내보내기와 팀 삭제를 할 수 있어(14 §2) 팀 설정 탭을 함께 보여 주고, 매니저에게는 멤버와 팀 삭제 구역만 보인다.

### 위임 흐름

알림 센터가 아직 없어서, 지명된 팀원에게는 팀 스페이스의 모든 탭 위에 "팀장 위임을 요청했어요" 안내와 팀 설정 링크를 띄운다. 만료는 저장된 요청 시각으로 그때그때 판단하며(서버 스케줄러 없이), 만료되면 팀장에게 "다시 지명해 주세요"를 보여 준다.

14 §5.2에 따라 위임이 진행 중이면 팀장의 승인·반려를 보류한다. 칸반에 승인 대기 태스크가 있으면 안내를 띄우고, 팀장이 승인하려 하면 이유를 알린다. 매니저의 개입 승인은 받는다.

### 삭제와 해체

팀을 지우거나 해체하면 칸반, 일정, 게시판, 공지를 함께 지우고 팀원의 소속을 비운다. 백엔드는 기존 `BaseSoftDeleteSupportEntity`로 소프트 삭제한다(14 §5.5). 팀 빌딩 모집 중이면 이 팀에 걸린 대기 제안을 사유 "팀 해체"로 만료한다(12 §5.4-4).

### 기획과 다르게 처리한 부분

14 §4.6의 팀 비밀번호는 넣지 않았다. 리뉴얼에서는 팀 합류가 팀 빌딩의 지원·스카우트로만 이뤄져 팀 비밀번호가 쓰일 곳이 없다. 백엔드 Team 엔티티에도 비밀번호 필드가 없다.

### 공통 보완

검사 중 두 가지를 함께 고쳤다. 사용자가 정한 이름 뒤 조사를 받침에 맞추는 `domain/josa.ts`를 추가해 "알파 스쿼드을 삭제했어요" 같은 문구를 바로잡았다(한글이 아닌 이름은 "을(를)"). 삭제·내보내기 같은 파괴적 보조 버튼이 기본색으로 보이던 문제는 `danger-ghost` 버튼 변형을 추가해 고쳤고, DESIGN.md 버튼 항목에 적었다.

## R11 결정 사항

### 채팅방 종류와 권한

15번 기획의 팀 방, DM, 그룹 방을 하나의 모델로 다룬다. 권한은 `domain/chat.ts`에 모아 화면과 목 규칙이 같이 쓴다.

| 종류 | 멤버 | 이름 바꾸기 | 멤버 추가 | 나가기 | 삭제 |
|---|---|---|---|---|---|
| 팀 방 | 팀 소속을 그대로 따른다 | 팀장 | 팀 합류로만 | 팀을 나가면 함께 빠진다 | 팀을 지우면 함께 지운다 |
| DM | 두 사람 | 없음 | 없음 | 가능 | 없음 |
| 그룹 방 | 만든 사람이 고른 멤버 | 만든 사람 | 방 멤버 | 가능 | 만든 사람 |

멤버가 아닌 방은 주소로 들어와도 404로 숨긴다. 개설자·매니저도 자기가 속하지 않은 팀 방의 내용은 볼 수 없다(15-D2 집계만).

### 팀 방 자동 생성

15-D3은 세션 확정(RESOLVED) 때 팀 방을 만든다고 적었다. 리뉴얼에서는 팀 빌딩 모집 중에도 팀이 먼저 꾸려지고 팀 스페이스가 열리므로, 팀이 생기는 즉시 팀 방과 팀 회의실을 만들었다. 결성에서 협업까지 끊김이 없게 하려는 같은 원칙(00 §5-2)을 더 이른 시점에 적용한 것이다. 팀 방 멤버를 따로 저장하지 않고 팀 소속에서 계산해, 팀 합류·내보내기·위임에 따라 방 멤버가 어긋나지 않는다. 그 대신 팀 소속 변화에 따른 입장·퇴장 안내문은 남기지 않는다. 그룹 방의 멤버 추가·나가기에는 안내문을 남긴다(15 §5.1).

### 채팅방(SCR-CHAT-01)

| 기능 | 처리 | 근거 |
|---|---|---|
| 방 목록 | 컨텍스트 내비 "커뮤니케이션"에 최근 방 6개와 안 읽은 수, 나머지는 채팅 목록 화면 | 15 §4.1 |
| 읽음 | 방에 들어오거나 새 메시지가 오면 읽음 처리 | 15 §4.1 |
| 보내기 | 화면에 먼저 띄우고, 실패하면 "전송 실패"와 다시 보내기·지우기 버튼 | 15 §5.1, alert() 폐기 |
| 검색 | 현재 방 안에서 찾고, 결과를 누르면 그 메시지로 이동해 강조·포커스 | 15 §4.2 |
| 방 설정 | 멤버, 멤버 추가, 알림 끄기, 이름 바꾸기, 나가기·삭제 | 15 §4.1 |
| DM 시작 | 카드 상세의 "DM 보내기". 이미 있는 DM이면 그 방으로 간다. 새 채팅방에서 한 명만 고르고 이름을 비워도 DM이 된다 | US-15-01 |

Enter로 보내고 Shift+Enter로 줄을 바꾼다. 한글 조합 중에는 Enter로 보내지 않는다(`isComposing`). 메시지 목록은 `role="log"`로 새 메시지를 알린다. 안 읽은 수 배지는 숫자를 화면에만 보여 주고, 보조기기에는 "안 읽은 메시지 N개"로 읽힌다.

목업은 실시간 연결이 없어 메시지를 4초, 방 목록을 8초마다 다시 가져온다. http 어댑터는 기존 SSE 이벤트(`CHAT_MESSAGE_RECEIVED`, `CHAT_MEMBER_JOINED/LEFT`)를 받을 때 같은 쿼리 키를 갱신하면 된다. 연결 상태 표시(연결 중, 재연결 중)는 SSE를 붙일 때 추가한다.

### 화상회의(SCR-VID-01)

들어가기 전에 카메라·마이크를 열어 미리보기를 보여 주고, 실패하면 오류 종류(권한 거부, 장치 없음, 다른 앱 사용 중, 미지원 환경)에 맞는 할 일을 안내한다(US-15-07). 장치 없이도 참여할 수 있다. 나가면 장치를 끄고 참여 기록을 지운 뒤 팀 스페이스로 돌아간다. 화면을 그냥 떠나도 퇴장 처리한다(15 §5.4 VideoMember 정리). 팀 스페이스 머리글의 "화상회의" 버튼으로 바로 들어온다(US-15-06).

실제 영상 연결은 LiveKit 연동 단계의 일이다. 목업에서는 다른 참여자의 영상과 소리가 없고 참여·퇴장 기록만 남으며, 화면에 그렇게 적었다. http 어댑터는 LiveKit 토큰을 응답 본문으로 받아 SDK에 넘기고 URL 쿼리에 토큰을 싣지 않는다(15-D5).

### 기획과 다르게 처리한 부분

기획의 회의 화면 사이드 채팅(STOMP)은 따로 만들지 않고 팀 채팅방 링크로 대신했다. 같은 팀의 대화가 두 곳으로 갈라지지 않게 하려는 결정이다. 팀 개요 멤버 아바타의 "DM 보내기" 메뉴는 카드 상세의 DM 버튼으로 대신했다(아바타를 누르면 카드 상세로 간다). 채팅 첨부(15-D6)와 반응 이모지(15-D1)는 넣지 않았다. 강사 대시보드의 채팅방 집계(15 §5.3 a)는 아직 넣지 않았다.

## R12 결정 사항

### 알림 기록 위치

알림은 각 목 규칙이 상태를 바꾼 뒤 어댑터가 `data/mock/notifyRules.ts`의 `on*` 함수를 불러 기록한다. 백엔드의 `NotificationService`(16 §7.3)와 같은 자리다. 행동한 본인에게는 보내지 않고, 받는 사람의 수신 설정에서 꺼진 계열은 기록하지 않는다(16 §6.4). 알림 쿼리는 워크스페이스 밖(`['notifications']`)에 두고, 목업에서는 8초마다 다시 가져온다. http 어댑터는 SSE 이벤트를 받을 때 같은 키를 갱신하면 된다.

| 이벤트 | 받는 사람 | 딥링크 |

| 지원·스카우트 접수, 수락·거절 | 팀장 또는 지원자·스카우트 대상 | 제안함, 수락이면 팀 스페이스 |

| 태스크 배정, 완료 요청·승인·반려 | 새 담당자, 팀장, 요청자 | 칸반의 해당 태스크 |

스위치는 `ui/Switch.tsx`로 공통화했다. 꺼진 트랙은 흰 바탕과 3:1 이상 대비가 나는 neutral-500을 쓰고, 상태를 "켬·끔" 글자로도 보인다. 앞 단계의 카드 공개 스위치와 채팅방 알림 스위치는 아직 각자 구현을 쓴다.

## R13 결정 사항

### 탭과 권한

설정은 `/ws/:wsId/settings` 풀페이지(13-D2)이고 탭은 `?tab=`으로 둔다. 권한 밖 탭 주소로 들어오면 일반 탭을 보인다. 넓은 화면은 왼쪽 탭 목록, 좁은 화면은 가로로 넘기는 탭 목록이다. 멤버에게는 탭 목록 없이 기본 정보와 나가기만 보이며, 내비 이름도 "워크스페이스 정보"로 바꿔 보인다.

| 탭 | 내용 | 여는 사람 |
|---|---|---|
| 일반 | 이름 수정(매니저 이상), 내 역할, 멤버·정원, 워크스페이스 나가기 | 모두 |
| 초대 | 현재 링크 복사, 만료일, 이 링크로 합류한 수, 재발급(30일, 7일, 만료 없음) | 개설자, 매니저 |
| 멤버 관리 | 이름·이메일 검색, 역할 표시, 행 메뉴로 임명·해제·개설자 넘기기·내보내기·차단 | 개설자, 매니저 |
| 차단 목록 | 차단한 사람과 날짜, 차단 해제 | 개설자, 매니저 |
| 보안 | 합류 비밀번호 정하기·바꾸기·없애기 | 개설자 |
| 위험 구역 | 워크스페이스 이름을 입력해야 하는 삭제 | 개설자 |

행 메뉴의 행동은 `domain/workspaceAdmin.ts`의 `memberActions`가 화면과 목 규칙에 같이 쓰인다. 자기 자신과 개설자에게는 아무것도 할 수 없다. 역할 변경과 개설자 넘기기는 개설자만 한다(13 §5.2). 기획은 매니저가 다른 매니저를 내보낼 수 있는지 정하지 않았다. 리뉴얼에서는 매니저가 멤버만 내보내거나 차단하게 해 운영자끼리 서로 내보내는 일을 막았다.

### 내보내기·차단·나가기의 정리 범위

세 행동 모두 워크스페이스 멤버십을 지우고 팀, 그룹 채팅방, 회의 참여, 대기 중인 지원·스카우트(만료 처리)를 함께 정리한다. 차단은 여기에 차단 기록을 더하고, 초대 링크로 다시 합류할 때 거부한다. 당사자에게는 `WS_MEMBER_BANNED` 알림이 가며, 이 알림은 계열을 꺼도 기록한다(16-D9).

| 대상이 팀장일 때 | 처리 |
|---|---|
| 스스로 나감 | 막는다. 팀장을 위임한 뒤 나간다(팀 나가기와 같은 규칙) |
| 내보내기·차단 | 가장 먼저 합류한 팀원이 팀장을 잇고 알림을 받는다 |
| 혼자 남은 팀장 | 팀을 해체한다 |

기획 §5.1은 차단 시 팀 LEFT 처리만 적고 팀장 공백을 다루지 않았다. 문제를 일으킨 팀장을 차단하지 못하면 운영이 막히므로, 내보내기·차단에는 자동 승계를 택했다. 확인 대화상자에 누가 팀장을 잇는지 미리 보인다.

개설자는 다른 멤버에게 넘긴 뒤에 나간다. 혼자 남은 개설자는 나갈 수 없고 삭제해야 한다(§5.3). 개설자 넘기기는 2단계 확인이다. 첫 단계에서 "나는 매니저가 된다"를 알리고, 둘째 단계에서 받는 사람 이름을 그대로 입력해야 넘기기 버튼이 켜진다. 마지막 매니저를 해제할 때는 "개설자 혼자 운영하게 된다"를 알리고 허용한다(13-D6).

### 초대 링크

재발급하면 이전 링크는 바로 무효가 되고, 그 링크로 들어오면 초대 랜딩이 만료 안내를 보인다(US-13-02). 만료 기간은 30일이 기본이고 "만료 없음"은 직접 골라야 한다(10-D2, 13-D3). 현재 링크가 만료됐으면 복사를 막고 재발급을 안내한다. 클립보드 권한이 없으면 링크를 선택해 두고 직접 복사하라고 알린다.

### 기획과 다르게 처리한 부분

| 항목 | 기획 | 리뉴얼 | 이유 |
|---|---|---|---|
| 합류 비밀번호 위치 | 초대 탭 안(개설자 전용) | 보안 탭. 초대 탭에는 있음·없음과 보안 탭 링크만 둔다 | 탭 권한을 탭 단위로 나누면 화면 안 권한 분기가 줄어든다 |
| 아이콘 변경 | 일반 탭 | 넣지 않았다 | 레일과 내비가 글자 아이콘을 쓰고, 이미지 저장소가 없다 |
| 팀 빌딩 사용 스위치 | 일반 탭 | 넣지 않았다 | 리뉴얼은 세션이 있으면 팀 빌딩을 켠 것으로 본다(R6). 세션 운영 화면이 이 역할을 한다 |
| 아카이브(US-13-07) | 위험 구역 | 넣지 않았다 | 모든 쓰기 경로를 막는 읽기 전용 전환이 필요하고, 90 결정상 M3 범위다 |
| 차단 멤버 작성물 익명화(13-D5) | "탈퇴한 멤버"로 표시 | 칸반 담당에서는 빠지고 게시글·메시지는 이름이 남는다 | 작성자 표시를 바꾸려면 게시판·채팅 화면 전체를 고쳐야 해 이후 단계로 미룬다 |
| 내보내기 알림 | 카탈로그에 없음 | 보내지 않는다 | 차단만 카탈로그에 있다. 내보내진 사람은 다음에 들어올 때 워크스페이스가 목록에서 사라진다 |

삭제는 팀과 그 안의 칸반·일정·게시판·공지, 세션과 지원, 채팅방과 메시지, 회의실, 초대 링크, 차단 기록, 그 워크스페이스의 알림을 함께 지운다. 나가기와 삭제 뒤에는 워크스페이스 목록을 새로 고친 다음 첫 화면으로 보내, 남은 워크스페이스나 무소속 랜딩으로 이어진다. `/me` 화면이 기억하던 마지막 워크스페이스가 사라졌으면 첫 워크스페이스로 대신한다.

## R14 결정 사항

### 마이페이지(SCR-MY-01)

기획은 마이페이지를 "유지"로만 적었다. 기존 화면의 프로필 확인에 17 §6.3의 열람권을 더해 다음처럼 구성했다.

| 묶음 | 내용 |
|---|---|
| 프로필 | 사진, 이름, 이메일. 이름은 대화상자에서 바꾸고(가입 규칙과 같은 2~50자), 사진은 카드 편집으로 연결한다 |
| 내 PR 카드 | 작성 전·작성 중·공개·비공개 상태와 그 의미, 카드 쓰기·편집 버튼 |
| 내 워크스페이스 | 이름, 역할, 소속 팀과 팀장 여부. 누르면 역할별 진입 경로로 간다 |
| 내 데이터 | 17 §6.1 항목마다 저장된 값과 공개 범위. JSON 내려받기, PR 카드 삭제 |

카드 내용은 카드를 공개했을 때만 워크스페이스 멤버에게 보이므로, 비공개면 공개 범위를 "나만(카드 비공개)"으로 표시한다. 내려받기 파일에는 비밀번호 해시 같은 인증 정보가 들어가지 않는다. 카드 삭제(17 §6.3 "PR 카드만 삭제")는 동의 기록까지 지워 카드 작성 전 상태로 돌린다. 갤러리와 팀 빌딩에서는 카드가 없는 사람으로 보인다.

### 계정 설정(SCR-MY-03)

| 묶음 | 내용 |
|---|---|
| 계정 정보 | 이메일, 로그인 방식(이메일, Google, 카카오) |
| 비밀번호 변경 | 지금 비밀번호, 새 비밀번호(가입 규칙과 조건 목록), 확인. 지금 비밀번호와 같으면 거절한다. 소셜 로그인만 쓰는 계정에는 비밀번호가 없다고 알린다 |
| 알림 수신, 음소거 | R12 그대로 |
| 계정 삭제 | 먼저 할 일이 있으면 목록으로 보이고 버튼을 막는다. 없으면 이메일 계정은 비밀번호, 소셜 계정은 이메일을 다시 입력해 삭제한다 |

계정 삭제의 "먼저 할 일"은 워크스페이스를 나갈 수 없는 상태와 같다. 개설자는 넘기거나 혼자 남은 워크스페이스를 삭제해야 하고, 팀원이 있는 팀장은 위임해야 한다(13 §5.3, 14 §5.4). 삭제하면 모든 워크스페이스를 나가고 카드, 비밀번호, OAuth 연동, 알림, 수신 설정을 지운 뒤 로그인 화면으로 보낸다. 이메일을 비워 같은 주소로 다시 가입할 수 있다.

### 기획과 다르게 처리한 부분

17 §6.3 흐름도는 계정 삭제를 "소프트 삭제 → 30일 유예 → 하드 삭제"로 그리고 유예 중 복원을 말한다. 그런데 §6.4 매트릭스는 이메일, 비밀번호, OAuth 식별자를 삭제 요청 즉시 지운다고 적었다. 로그인 수단이 없으면 복원할 방법이 없으므로, 리뉴얼은 화면에서 삭제를 되돌릴 수 없는 행동으로 다룬다. 30일 유예는 남은 기록(메시지, 게시글, 멤버십 이력)을 익명화하기 전 서버가 보관하는 기간으로 해석했다. 목업은 이름을 그대로 남기며 30일 뒤 익명화 배치는 서버 몫이다. 계정 삭제 화면 문구는 실제 서비스 기준("30일 뒤 작성자가 탈퇴한 사용자로 바뀐다")으로 적었다.

마케팅 수신 동의(17 §6.2)는 마케팅 발송이 없어 넣지 않았다. 계정 정보의 가입일은 계정 모델에 가입 시각이 없어 넣지 않았다.

### 함께 고친 것

R10 팀 삭제 확인 라벨이 "팀 이름 알파팀을"처럼 조사를 고정해 받침 없는 이름에서 틀렸다. 워크스페이스 삭제와 같이 "확인을 위해 팀 이름을 입력해 주세요: 알파팀"으로 바꿨다.

## R15 결정 사항

### 가입 동의(17 §6.2, 17-D6)

R7 가입 화면에는 17 §6.2가 필수로 정한 이용약관·개인정보 처리방침 동의와 17-D6의 만 14세 이상 확인이 빠져 있었다. 가입 3단계(계정 정보)에 세 항목과 "모두 동의해요"를 더했다. 문서 링크는 새 탭에서 열어 입력 중인 가입 정보를 잃지 않게 했다. 하나라도 빠지면 가입을 막고 "모두 동의해요"로 포커스를 옮긴다. 서버(목 규칙)도 같은 조건을 다시 확인하고, 동의 시각과 문서 판(`POLICY_VERSION`)을 기록한다.

소셜 로그인은 제공자 화면에서 바로 계정이 생기므로 가입 폼을 거치지 않는다. 동의 기록이 없는 계정은 로그인한 화면에 들어올 때 `/agreements`로 보내 같은 세 항목을 받고, 원래 목적지로 돌려보낸다. 동의하지 않으면 로그아웃할 수 있다. 시드 계정은 동의한 상태로 둔다.

`RequireConsent` 가드는 동의 조회를 기다리며 화면을 막지 않는다. 대부분은 이미 동의했으므로 모든 화면에 왕복 한 번을 더하지 않으려는 결정이다. 동의가 없다고 확인되면 그때 옮기므로, 소셜 첫 로그인 직후 짧게 화면이 보였다가 동의 화면으로 바뀔 수 있다. 조회에 실패해도 막지 않고 서버가 쓰기 요청에서 다시 확인하는 것을 전제로 한다.

### 정책 문서

`/privacy`와 `/terms`는 로그인하지 않아도 열리고, 앱 셸 없이 읽기 폭에 맞춘 단독 화면이다. 17-D3에 따라 법률 검토 전 표준 양식 초안이며 문서 맨 위에 그 사실을 밝혔다.

| 문서 | 구성 | 근거 |
|---|---|---|
| 개인정보 처리방침 | 10개 조항. 수집 항목 표(17 §6.1), 계정 삭제 시 처리 표(17 §6.4), 외부 서비스(Gmail 인증 메일, Google·카카오 로그인, 백업 스토리지), 권리 행사 방법(마이페이지 열람·내려받기, 카드·계정 삭제) | 17 §6.7 |
| 이용약관 | 서비스 범위, 콘텐츠 권리, 이용 제한, 중단·변경, 책임 한계, 가입 연령 | 17 §6.8, 17-D6 |

개인정보 보호 책임자의 연락 창구는 정해지지 않아 "정식 서비스 공개 때 적는다"고만 썼다. 마이페이지 "내 데이터"에 약관 동의 시각과 판을 더했고, 계정을 삭제하면 동의 기록도 지운다.

### 남은 한계

로그인 화면의 `redirect`는 소셜 로그인을 거치면 보존되지 않는다(R7부터). 초대 링크로 들어온 소셜 첫 로그인은 초대 합류가 동의보다 먼저 일어난다. 문서 판이 바뀌었을 때 다시 동의를 받는 흐름은 넣지 않았다.

## R16 결정 사항

### 워크스페이스 공지

02 §2.3은 컨텍스트 내비 워크스페이스 묶음에 "공지"를 두고, 16 §5.4는 공지 알림의 착지를 "SCR-TM-05 또는 SCR-WS-01(해당 공지)"로 정했다. 워크스페이스 전체 공지는 홈의 최근 공지에 시드로만 있었고 쓸 화면이 없었다. 화면 ID가 따로 없어 `/ws/:wsId/announcements`에 두었다.

| 항목 | 처리 |
|---|---|
| 읽기 | 멤버 모두. 전체 공지만 최신순으로 보이고 팀 공지는 각 팀 스페이스에 둔다 |
| 쓰기·수정·삭제 | 개설자·매니저. 수정하면 "수정됨"을 붙인다 |
| 알림 | 올리면 쓴 사람을 뺀 멤버 모두에게 `ANNOUNCEMENT_CREATED`, 링크는 `?id=`로 그 공지 |
| 강조 | `?id=`로 들어오면 그 공지로 스크롤하고 포커스를 옮긴다. 지워졌으면 "찾는 공지가 없어요"를 알린다 |
| 홈 | 최근 공지 항목을 링크로 바꿨다. 전체 공지는 강조 주소로, 팀 공지는 팀 공지 탭으로 간다. "전체 공지 보기"를 더했다 |
| 대시보드 | 이상 신호 위젯에 "전체 공지 쓰기"(작성 대화상자를 연 채로 이동)와 차단 이력의 "차단 목록" 링크를 더했다. R6에서 남겨 둔 이상 신호 행동이다 |

공지 목록·작성·수정·삭제는 `features/announcements/AnnouncementBoard.tsx`로 묶어 팀 공지(SCR-TM-05)와 함께 쓴다. 제목·본문 편집 대화상자는 `features/teamSpace/TextEditorModal.tsx`로 옮겨 게시판도 같이 쓴다. 공지 삭제 확인 버튼은 빨간 확인(`tone="danger"`)으로 바꿨다.

시드의 전체 공지 두 건에 본문과 작성자 계정을 채웠다. 저장소 구조는 바꾸지 않아 mock DB 버전은 그대로다.

## R17 결정 사항

앞 단계에서 남은 한계로 적은 것 중 세 가지를 고쳤다.

### 삭제된 대상으로 가는 딥링크(16 §6.4)

R12는 삭제된 대상 딥링크를 각 화면의 404로 처리했다. 16 §6.4는 "삭제된 항목" 토스트와 상위 화면 이동을 정했으므로 그대로 바꿨다. 공통 처리는 `screens/system.tsx`의 `MissingRedirect`다. 토스트에는 새 `info` 종류(파란 안내, 6초 뒤 사라짐)를 쓴다.

| 대상 | 옮기는 곳 | 안내 |
|---|---|---|
| 게시글 | 게시판 | 삭제됐거나 볼 수 없는 글이에요 |
| 칸반 태스크(`?task=`) | 같은 칸반, 주소에서 task를 뺌 | 삭제됐거나 볼 수 없는 태스크예요 |
| 채팅방 | 채팅 목록 | 삭제됐거나 볼 수 없는 항목이에요 |
| 회의실 | 워크스페이스 홈 | 삭제됐거나 볼 수 없는 항목이에요 |
| 팀 스페이스 | 워크스페이스 홈 | 해체됐거나 볼 수 없는 팀이에요 |
| 팀 모집 상세 | 팀 빌딩 홈 | 해체됐거나 볼 수 없는 팀이에요 |
| 멤버 카드 상세 | 멤버 카드 | 워크스페이스를 떠났거나 볼 수 없는 멤버예요 |
| 워크스페이스 공지(`?id=`) | 같은 목록 | 찾는 공지가 없어요(R16) |

비공개 자원(남의 팀 방, 팀원이 아닌 팀 스페이스)도 같은 문구로 다뤄 존재 여부를 드러내지 않는다(02 §4). 내가 방금 지우거나 나가서 대상이 사라진 경우에는 결과 토스트가 이미 떴으므로 안내 없이 옮긴다. 화면이 그 대상을 한 번이라도 보여 줬는지를 기억해 구분한다. 칸반은 내가 지운 태스크와 다른 사람이 지운 태스크를 나눠 안내한다. 워크스페이스 자체가 없는 주소는 옮길 상위가 없어 404를 유지한다.

### 스위치 통일

R12에서 만든 `ui/Switch.tsx`를 카드 공개 스위치(SCR-MY-02)와 채팅방 새 메시지 알림 스위치(SCR-CHAT-01)에도 썼다. 이제 모든 스위치가 같은 크기·대비·"켬·끔" 글자와 라벨·설명 연결을 갖는다. 태스크 삭제 확인 버튼도 빨간 확인으로 맞췄다.

### 소셜 로그인 목적지 보존

로그인 화면의 `?redirect=`는 소셜 제공자 화면을 다녀오면 사라졌다(R7부터). 떠나기 전에 sessionStorage에 두고 콜백에서 한 번 꺼내 쓴 뒤 지운다. 초대 코드 보존과 같은 방식이다. 소셜 첫 로그인이면 동의 화면(R15)을 거쳐 같은 목적지로 간다.

### 회귀 검사 갱신

R3·R5·R8·R10·R11·R9 흐름 검사 중 "404 화면"을 기대하던 7건을 "상위 화면으로 옮기고 안내"로 바꿨다. 남의 팀 방에 매니저가 들어오는 경우 메시지 내용이 보이지 않는지도 함께 확인한다.

## R18 결정 사항

### 시각 기반 알림

R12에서 서버 스케줄러가 필요해 미룬 알림 세 가지를 넣었다. 백엔드에서는 스케줄러가 정해진 시각에 보내고, 목업은 서버가 없으므로 알림을 조회할 때(벨 배지와 알림 센터의 주기 조회) `data/mock/timedRules.ts`의 `runTimedEvents`가 "지금 보내야 할 알림"을 계산한다. 보낸 것은 `sentTimedEvents`에 기록해 다시 보내지 않는다. 마감 시각이나 일정 시각이 바뀌면 기록 키도 바뀌어 새 시각 기준으로 다시 보낸다.

| 이벤트 | 조건 | 받는 사람 | 딥링크 |
|---|---|---|---|
| `TB_SESSION_CLOSING_SOON` | 모집 중 세션 마감 24시간 전부터 마감 전까지(16-D3) | 팀이 없는 멤버 | 팀 빌딩 홈 |
| `TB_UNASSIGNED_WARNING` | 같은 시점, 미배정 멤버가 있으면 | 개설자·매니저 | 세션 운영 |
| `SCHEDULE_REMINDER` | 일정 시작 5분 전부터 시작 전까지(16-D4) | 팀 일정은 팀원, 개인 일정은 만든 사람 | 일정 목록의 그날 |

16 §5.1 카탈로그는 `TB_UNASSIGNED_WARNING`의 수신자를 "미배정 멤버"로 적었지만, 같은 시점에 미배정 멤버는 `TB_SESSION_CLOSING_SOON`을 받는다. 16 §2 액터 표가 매니저·개설자의 수신 항목으로 "미배정 경고"를 적었으므로, 경고는 운영진에게 미배정 인원 수와 함께 보내고 세션 운영 화면으로 잇는다. 세 알림 모두 수신 설정을 따른다. mock DB 버전을 12로 올렸다.

일정 리마인더는 기획(14 §4.3)의 "일정 생성 시 리마인더 설정"과 달리 모든 일정에 5분 전 알림을 보낸다. 16-D4가 사용자 설정을 복잡도 때문에 택하지 않았기 때문이다.

## R19 결정 사항

### 지원 알림 묶음(16 §6.3, 16-D7)

같은 팀에 한 시간 안에 온 지원은 팀장에게 한 건으로 묶어 "데이터 크루에 2명이 지원했어요"처럼 보낸다. 묶음은 읽지 않은 동안만 이어지고, 읽었거나 묶음을 시작한 지 한 시간이 지나면 새로 쌓는다. 벨 배지도 묶음 한 건으로 센다.

### 알림 묶음 구조

R12의 채팅 묶음은 문구를 정규식으로 고쳐 쓰는 방식이었다. `notify`의 묶음 설정을 `group: { key, windowMs?, title(count) }`로 바꿔 채팅과 지원이 같은 구조를 쓴다. 묶음 기간을 재려고 알림에 `groupStartedAt`을 더했다. 채팅 묶음은 기간 없이 방에 들어가 읽을 때까지 이어진다(R12 결정 유지).

### 작성자 익명 표시 점검(13-D5)

13-D5는 차단된 멤버의 칸반 담당과 게시글 작성자를 익명으로 표시하라고 정했다. 확인해 보니 이미 지켜지고 있어 코드는 바꾸지 않았다.

| 위치 | 표시 | 근거 |
|---|---|---|
| 칸반 담당자 | 내보내기·차단·나가기 때 담당에서 빠진다 | R13 `detach` |
| 게시글·댓글·태스크 기록 작성자 | 지금 팀원이 아니면 "이전 팀원" | R9 `nameOf` |
| 채팅 메시지 작성자 | 지금 방 멤버가 아니면 "나간 멤버" | R11 |

차단과 단순 이탈을 구분하지 않고 같은 문구를 쓴다. 차단 사실을 다른 멤버에게 드러내지 않는 편이 낫다고 봤다. 워크스페이스 공지의 작성자 이름은 저장 시점 이름을 그대로 보인다. 공지는 개설자·매니저만 쓰므로 차단 대상이 되는 경우가 드물다.
